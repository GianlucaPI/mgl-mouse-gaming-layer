[2026-11-17] Phase 1 - First real test session (BLE, Terminal, outside WoW)
  - Input Monitoring granted to Terminal; Accessibility not yet.
  - Mouse side buttons emit HID keyboard usages (seen: Y, U, I, P) on the same
    BLE interface; each report also re-sends Consumer AC Pan (0x0C/0x238) = 0.
  - ROOT CAUSE CONFIRMED: Left Shift held from t=1855ms to t=9595ms, yet the
    mouse keyDown/keyUp events for Y/U/I/P carry flags=0x100 (no Shift).
  - Worse: CGEventSourceFlagsState(.hidSystemState) and (.combinedSessionState)
    also read [] at the time of the mouse events while Shift is still held.
    => macOS global modifier state is not reliable here; the HID system appears
       to adopt the (empty) modifier state of the mouse's keyboard collection.
    => The probe's "MISSING" detector (based on hidSystemState) never fired:
       it must track modifiers itself from flagsChanged events.
  - keyboardType distinguishes devices: Aerox 9 = 40, MacBook keyboard = 92.
  - Real keyboard events are fine (Ctrl+C carried Ctrl).
  - DECISION: Phase 2 = Strategy A with our own modifier tracking:
      * track per-keyboardType modifier state from flagsChanged events
        (the mouse never emits flagsChanged);
      * OR the union of held modifiers into every keyDown/keyUp (no-op for
        events that already carry them).
    Open question: does WoW read event flags or the global state? If the
    latter, add an optional "sync" mode that also restores the global state.

[2026-11-17] Phase 2 - Mouse-event patching + opt-in global-state sync
  - Rationale: even though key patching works, the probe showed macOS's global
    modifier state (hidSystemState/combinedSession) reads [] after a mouse key
    while Shift is still held, until the next real modifier event. Exposed:
      a) mouse clicks/scroll right after a side button (e.g. Shift-click to
         link an item in WoW) inherit the empty state;
      b) code that polls the current modifier state (NSEvent.modifierFlags,
         some addons / macro conditionals) instead of reading event flags.
  - (a) ModifierPatcher now also patches left/right/other mouse down/up and
    scrollWheel flags. ON by default (--no-mouse to disable): same semantics as
    key patching, only adds modifiers really held.
  - (b) --sync-global (OFF by default): after a patched key event, a block on
    the main queue (runs right after the tap callback returns) posts a
    synthetic flagsChanged at the HID tap with flags = held | 0x100 and keycode
    of a held modifier (ModifierFlags.representativeKeyCode, side-aware).
    Events are tagged eventSourceUserData = 0x4D474C ("MGL"); our taps ignore
    them, so they never feed the tracker (no feedback loop). Syncs coalesce.
    No stuck modifiers: tap callbacks and the sync block run serially on the
    same run loop, so the sync always uses the latest tracked state.
    Opt-in because a synthetic modifier "press" may count towards
    "press modifier twice" shortcuts (dictation, Sticky Keys...).
  - mgl-probe: now also logs mouse-button downs (MISSING check applies), tags
    synthetic MGL events [MGL-SYNTH], summary counts both.
  - Tests: 15 passing (3 new for representativeKeyCode).
  - NOT yet verified on hardware.
  - NEXT (user): `mgl -v` + `mgl-probe watch --session --steelseries`:
    hold Shift, press side button, then click -> click must carry Shift.
    Then `mgl -v --sync-global`: after a side button, the probe's hidState/
    session columns should show Shift again. Then move on to Phase 4 (config,
    per-app activation); Phase 3 (seize) is not needed.

[2026-11-17] Phase 5 - User test: app OK; Shift + wheel / middle click broken
  - Reported: MGL.app installs and runs, side buttons work. NOT working in
    WoW: Shift + wheel up, Shift + wheel down, Shift + middle click. Wheel up
    needs ~3 notches before it "works".
  - Research: macOS converts Shift + vertical wheel (non-continuous mice) into
    a HORIZONTAL scroll and keeps Shift in the flags; games therefore never
    see SHIFT-MOUSEWHEELUP/DOWN. Known for WoW/Minecraft/Dear ImGui; existing
    workaround tools drop Shift from scroll events (games track Shift via
    flagsChanged anyway). Refs: Apple discussions thread 253391792, Dear ImGui
    commit "Fix mouse wheel axis swap when using SHIFT on macOS".
  - Code review findings:
      1. MGL itself ADDS Shift to scroll events when the (reset) global state
         lacks it, which can trigger the conversion; combined with the global
         modifier state being reset by the mouse's own reports, the conversion
         happens inconsistently -> likely cause of the "3 notches" behavior.
      2. mgl-probe could not diagnose any of this: scroll events were not
         tapped, the HID wheel usage (page 0x01 / 0x38) was filtered out, and
         otherMouseDown did not report WHICH button.
  - Fix: new profile option `shiftScroll` (ScrollFix.swift):
      system               leave macOS behavior (default; right for browsers)
      vertical             if the tick arrives horizontal-only, move the
                           deltas back to axis 1 (line, fixed-point, pixel;
                           same sign) and strip Shift (both sides) from the
                           scroll event so nothing converts it again
      vertical-keep-shift  move back to vertical, keep Shift in the flags
    Applies only to non-continuous scroll (wheel mice; trackpads untouched)
    while Shift is held (our tracker) or present in the event. Other held
    modifiers are still added. Example WoW profile now uses "vertical".
    Verbose CLI logs "fixed shift-scroll  v=../h=.. -> ..". New stat counter.
  - The user's own ~/Library/Application Support/MGL/config.json got
    "shiftScroll": "vertical" in the WoW profile (backup: config.json.bak).
  - mgl-probe: taps scrollWheel (axes v/h as line/fixed/pixel, wheel vs
    continuous, direction, "<-- SHIFT→HORIZONTAL" marker) and logs mouse
    button numbers (0 left, 1 right, 2 middle, 3+ other); HID log now shows
    the wheel usage.
  - Tests: 33 passing (7 new in ScrollFixTests).
  - Middle click: no code bug found (otherMouseDown is patched like the other
    buttons). Needs probe data: it may not be button 2 on the Aerox 9 or WoW
    may need something else.
  - NOT verified on hardware yet.
  - NEXT (user): rebuild + reinstall the app, test Shift+wheel up/down in
    WoW; if still failing try "vertical-keep-shift". Run
    `mgl-probe watch --session --steelseries` while pressing Shift + wheel /
    Shift + middle click (with MGL running) and share the output.

[2026-11-17] Phase 5 - Shift + wheel: AppKit converts inside the app; wheel 0.1/notch
  - Probe `watch --late --steelseries` with MGL running (Shift + wheel):
        HID wheel usage 0x01/0x38 val=+1 / -1
        late tap: "scroll wheel up   flags=[Shift(L)] axes v=1/0.10/1px h=0 wheel"
                  "scroll wheel down flags=[Shift(L)] axes v=-1/-0.10/-1px"
  - FINDING 1: at the LAST tap stage the tick is still VERTICAL with Shift.
    So the conversion to horizontal is not in the WindowServer but in AppKit,
    inside WoW, when the NSEvent is built. No tap can undo it afterwards.
    AppKit only does it for non-precise scrolls (trackpads are not swapped).
  - FINDING 2: each notch is worth only 0.10 lines (fixed-point delta), 1 px.
    Games accumulating deltaY need several notches: very likely the reported
    "wheel up must be turned ~3 times before it works".
  - Fix (late tap, WheelFix.apply, pure + tested):
      * shiftScroll "vertical-keep-shift": keep vertical axis + Shift, ensure
        Shift bits, and mark the event scrollWheelEventIsContinuous = 1
        (precise) with >= 10 px per line, so AppKit does not swap it;
      * shiftScroll "vertical": strip Shift (unchanged idea);
      * new profile option normalizeWheel: fixed-point delta >= line delta
        per axis (0.1 -> 1.0), accelerated values kept. ON in the example WoW
        profile and in the user's config (backup config.json.bak2).
    Only notched (non-continuous) wheel events are touched; HID-stage scroll
    special-casing removed (normal modifier patching only).
  - mgl-probe --late now appends at the TAIL of the annotated-session stage,
    so it shows events after MGL's late tap; precise ticks print "PRECISE".
  - Tests: 39 passing (WheelFix suite rewritten with the real 0.10 values).
  - Release CLI tools rebuilt. NOT verified in WoW.
  - Risk: WoW might handle precise scrolls differently (e.g. needs more
    pixels). If so: tune pixelsPerLine or try "vertical".
  - NEXT (user): build-app.sh --install; test wheel (1 notch) and Shift +
